## 1. In-app "new version" prompt (replaces upstream's update check on our builds)

Why: TestFlight auto-update never fires for her, and upstream's 检查更新 checks
Predidit's GitHub releases, which is wrong for the fork.

**Where "latest" lives:** a public static file on HK,
`https://hk.kaic5504.com/app/latest.json` →
`{"build": 15, "version": "3.0.0", "minBuild": 15, "notes": "…", "publishedAt": "…"}`.
- `minBuild`: any build below it **must** update. A build at or above `minBuild` but
  below `build` gets the optional prompt. A floor rather than a per-release
  `required` flag, so a required 16 followed by an optional 17 still forces someone
  on 15.
- HK Caddy: `handle /app/*` → `file_server` rooted at `/srv` with
  `Cache-Control: no-store`. Mirror the change in `server/deploy/hk-relay.Caddyfile`.
- Public on purpose: needs no library key, so it works on first launch and is fast
  from mainland China (33 ms).

**How the app knows its own build:** Flutter's `appBuildNumber` (from
`package:flutter/services.dart`, set by `--build-number=$BUILD_NUMBER`, which
codemagic.yaml already passes). Same mechanism `ApiEndpoints.version` uses for
`appBuildName`. No new dependency. Null or unparsable (local/debug builds) → never
prompt.

**Code (fork file `lib/services/update/testflight_update.dart`):**
- `TestflightUpdate.check()` → GET latest.json (8 s timeout, no-store). If
  `build > KAZUMI_BUILD`, return the info.
- Optional update: `KazumiDialog` "有新版本 3.0.0 (15)" + notes, buttons **稍后** and
  **去更新**. Shows on **every app open** until updated; 稍后 only closes it for this
  launch.
- Required update: "需要更新到 3.0.0 (15)" + notes, only **去更新**. Can't be dismissed
  (no barrier tap, back gesture blocked), stays up after returning from TestFlight,
  and is re-checked when the app comes back to the foreground.
- Grace period: a required update acts as optional for the first 30 min after
  `publishedAt`, because Apple can still be processing the build and she'd be locked
  out with nothing to install.
- 去更新 opens `itms-beta://beta.itunes.apple.com/v1/app/6818711929` via url_launcher.
  If that can't open, fall back to `https://beta.itunes.apple.com/v1/app/6818711929`.
- Network failure, HK down or malformed JSON → no prompt, never a lock-out.
- Manual 检查更新 (about page) runs the same check: "已是最新版本 (15)" toast or the dialog.

**Hook points (upstream files, minimal diff):**
- `MyController.checkUpdate`: on iOS, call `TestflightUpdate` instead of `AutoUpdater`.
- Windows/other platforms: our PC build is installed by hand, so skip upstream's
  Predidit auto-prompt there too (manual check shows the latest iOS build number
  only). Keep upstream code paths intact for a clean merge.
- `init_page.dart` startup check: keep `runStartupUpdateCheck`. On iOS it must
  ignore the `autoUpdate` setting's off state, or skip the setting if it defaults
  off. Check its default first.

**Release step (every TestFlight build from now on):**
- Codemagic writes `$BUILD_NUMBER` to an artifact (`build/ios/ipa/build_number.txt`).
- `python scripts/codemagic.py publish-latest` reads that artifact from the
  finished build and writes `/srv/app/latest.json` on HK over ssh (`KaiCHK`), with
  notes passed on the command line. `--required` raises `minBuild` to this build;
  without it `minBuild` keeps its previous value.
- 3.0.0 (15) itself ships as optional (nobody has the prompt yet anyway).
- Publish when Codemagic passes. Apple takes 5–30 min to process, so the dialog
  says: "TestFlight 里还没出现的话，等几分钟再点更新".
- Add this step to CLAUDE.md "Building and shipping" and to memory.

**Tests:** unit tests for parsing latest.json, build compare (newer, same, older,
0/unknown, malformed JSON, timeout → no prompt), required vs optional from
`minBuild` (incl. required 16 then optional 17 seen from 15), the 30 min grace, a
missing `minBuild` → optional, and that the deep link URL is exact. Widget test that
the required dialog has no 稍后 and survives a back gesture.

## 2. Resumed library downloads also use HK

Bug seen 2026-10-06: downloads queued by an old build and resumed from 下载管理
only knew Hetzner (`MirrorRegistry` is filled only when 一起看 starts a download in
the current session). Result: 24 connections to Hetzner at 2.6 MB/s, 21% resent,
none via HK.

Fix: when the download manager starts a pre-upscaled task whose URL is a library
episode URL (`LibraryApi.ownsUrl`), and no mirror set is registered, build the set
from the last known library config (server + `mirrors`, cached in settings by
`_applyConfig`). Rewrite the host for each mirror, keeping the same path and token.
Order: relays first until speeds are measured. The `MirrorSet` explore/EWMA logic
then picks the faster one per part.

Tests: mirror set derived from a resumed URL; no mirrors for non-library URLs; the
token is preserved; an old Hetzner-only URL gains HK.

## 3. Streaming from 一起看 waits for the HK check

Bug: tapping an episode before `_rankHosts()` finishes (up to 10 s) streams from
Hetzner for the whole episode (mpv has a single URL; `_hosts` is empty → `baseUri`).

Fix:
- Keep the ranking `Future` in `LibraryController`. `openEpisode` awaits it, capped
  at 10 s.
- While unranked, `_videoUrls` orders relays first instead of the server first.
- Show the existing loading state during the wait (no new UI).

Tests: unranked order puts relays first; `openEpisode` uses the ranked first host.
